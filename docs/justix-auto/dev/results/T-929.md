## Installation and storage contract

The trusted outer runner must verify the original template/base bytes and the
release manifest/profile and evidence references before invoking psql `-X`.
Required variables are listed at the template's start: owner/runtime, template
and shared/base artifact hashes, base manifest/profile hashes, baseline kind,
evidence/approval/backup/stopped-runtime references and nonzero request UUID.
SQL validates shape and binds supplied immutable evidence; it cannot hash its
own input, verify an external manifest, prove what historically ran, authorize
an attestation or establish that processes stopped. A valid-looking false hash
or reference is not independently authenticated by this template.

The exact private database/login/runtime, database/schema/table owners, complete
two-column clean version-1 ledger rowset, owner mechanics marker/default and
legacy narrow mechanics grants are mandatory. Reachable NOINHERIT roles, direct,
PUBLIC, column and grant-option privileges are checked. Non-owner default grants
are rejected before new objects are created. Existing additive messaging must
explicitly remain legacy. An existing custody store without history requires a
separate reviewed adoption; T-934 consumes history already present before later
custody activation. No permissive custody or owner-head fallback was introduced.

The complete template has explicit BEGIN/COMMIT, five-second lock/statement/
transaction bounds, and obtains the common one-argument advisory key in that
same psql transaction: first eight SHA-256 bytes of UTF-8
`justixauto:owner-install:v1:` plus the exact database, signed big-endian int64.
Transaction-scoped locking conflicts with the driver's session-scoped lock on
the identical key and releases on commit/rollback/disconnection. This does not
claim uninterrupted locking across different runner connections or cooperation
from arbitrary administrative DDL.

Three owner-local tables expose schema USAGE and table SELECT to the runtime:

- `compatibility`: singleton owner/database/runtime, format revision 1,
  template/shared/base hashes, baseline version 1 and provenance kind, immutable
  evidence references, request UUID and finite installation timestamp.
- `artifacts`: private version PK, unique owner-relative filename, SQL hash,
  exact predecessor version/hash, feature identity/digest, unique request,
  artifact-manifest and installing-profile digests, finite completion time and
  provenance. Baseline seed is only version 1 and matches compatibility evidence.
  Prior installing-profile identity is retained when a later bundle is installed.
- `feature_contracts`: contract ID/revision PK, unique private migration version
  and digest. Invoker insert guards require the exact owner and dirty target
  ledger above the retained artifact head. Subsequent artifact guards serialize
  on the ledger, require its exact dirty target and latest recorded predecessor,
  and use an immediate matching feature-marker FK.

UPDATE/DELETE/TRUNCATE invoker guards cover all three tables, including ordinary
migration DML and empty-table statements. Runtime cannot insert, delegate the
SELECT grant, alter objects or disable guards. Trusted migration owners remain
DDL administrators; this is not tamper-proof evidence against the database owner.

Feature DDL must write its approved literal marker atomically with schema work.
The later driver must insert a receipt and clean its ledger in one transaction
only after successful exact-byte execution and feature object/grant validation.
This template alone cannot prove that a marker's claimed feature objects exist
or enforce the driver's command sequence against trusted owner SQL. It performs
no dirty repair, reapply, ledger reset, inferred history or automatic adoption.
Unknown connection outcomes require authoritative request/hash/history checks
on a fresh bounded connection; they never authorize template replay.
