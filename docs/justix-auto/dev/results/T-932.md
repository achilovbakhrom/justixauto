## Driver and T-933 handoff

`NewDriver(ctx, ownedConn, Config)` is inert: it validates trusted configuration
shape but queries/mutates nothing. On success it takes exclusive ownership of
one native `*pgx.Conn`; callers must stop using that connection. Config contains
a sealed `persistence.Profile`, canonical absolute repository/owner roots,
bounded provenance reference and explicit `FreshBootstrap`. No URL driver is
registered; `Open` and `Drop` are unsupported. No caller SQL predicate/readiness
callback is accepted. Parent cancellation and fixed operation deadlines are
captured because migrate's public methods do not take contexts.

`Lock` starts its five-second context before original-file verification and
owner/catalog/history preflight. It verifies every private SQL and adjacent
manifest, including already installed files, using the existing strict typed
manifest verifier. It retains verified original bodies, also hashes original
shared/template files, rejects symlink components/nonregular leaves, and checks
exact supported legacy shared identities through revision 4. Files are checked
again before every dirty write; `Run` checks the bytes after the engine boundary.
These are trusted local release files, not a hostile concurrent filesystem
fencing mechanism. Custody or shared revisions beyond 4 remain unsupported.

The one owner advisory key is the signed big-endian first eight SHA-256 bytes of
UTF-8 `justixauto:owner-install:v1:` plus the exact database. Acquisition uses
bounded `pg_try_advisory_lock` polling on the owned connection, without an
acquisition goroutine. The fixed owner-side preflight runs under this same lock.
Actual `pg_locks` ownership is checked before dirty work, before/after execution
and before finalization; an artifact releasing the lock fails closed. Unlock
checks PostgreSQL's release result. Uncertain ownership/cancellation closes the
connection. T-933 must keep the actual engine `LockTimeout` longer than five
seconds; the tested upstream default is fifteen seconds.

`Version` inspects the complete two-column bigint/boolean ledger and its full
rowset. Missing, malformed, multiple or invalid rows are not a maximum-version
fallback. Only an explicitly created empty fresh ledger can return NilVersion.
Under the installation lock, fresh bootstrap requires a one-artifact v1 profile,
verified-installation baseline, absent ledger/mechanics/history and the already
installed exact shared base. It creates the initial empty ledger explicitly.
An existing clean v1 without history cannot use this fresh exception or start a
feature upgrade.

Dirty transition uses a ReadCommitted transaction on the same connection,
locks/rechecks the complete previous clean ledger/history, verifies the exact
next artifact and marks its target dirty. It verifies the resulting row before
commit. A pending attempt binds version, exact SQL/profile digests, unique request
UUID and provenance. The fresh v1 request uses the sealed baseline request UUID;
later requests are new UUIDs. `LastAttempt` exposes an immutable attempt value
with version/request accessors; it is evidence, never authorization to replay.

`Run` requires that pending dirty item, compares full nonempty original bytes,
and executes exactly one `PgConn().Exec(...).ReadAll()` batch. It adds no outer
transaction and never splits semicolons, preserving the file's own BEGIN/COMMIT.
The connection must be idle before and after. The pinned engine supplies an
`*io.PipeReader`; cancellation directly closes that pipe. Standard bytes/string
memory readers are also admitted. Arbitrary blocking Reader callbacks are
unsupported rather than launching an unbounded read goroutine. Remaining failed
transactions receive bounded rollback cleanup; any failed/ambiguous execution
closes/poisons the instance and never sets successful-Run state.

Only the matching successful Run permits clean finalization. One ReadCommitted
transaction on that same connection locks/verifies the dirty target, validates
the exact committed marker and typed objects/grants, appends the immutable
artifact receipt, and changes the single ledger row to clean. It checks the
affected-row counts, resulting exact receipt/history and complete clean ledger
before committing once. A trigger suppressing either receipt insertion or the
clean update therefore cannot report completion or leave a partial receipt.
The unchanged fresh v1 is the sole no-history/no-artifact-receipt exception: its
original mechanics marker/default and grants must validate before clean. The
successful base execution evidence must be retained by the outer runner before
the separately invoked original history template. There is no automatic template
installation or inference of baseline attestation.

Direct Force/clean without Run, lower/skipped targets, duplicate pending work,
empty/substituted source, dirty repair, Down/Drop and automatic retries cannot
complete the protocol. Existing receipts keep their original request, time and
installing-profile digest when a later bundle is installed. A new missing lower
item in `[1,17] -> [1,12,17]` rejects before dirty mutation; the engine cannot
silently skip it as an already-current head.

`Reconcile` takes a fresh exclusively owned owner connection, revalidates the
trusted files and owner identity, acquires the identical bounded lock, and reads
ledger/history using a ReadCommitted read-only transaction. It closes that
connection afterwards. Clean target plus exact request/SQL/profile/provenance
and complete matching history returns `RecordedCompletion`. Dirty target with
exact retained prior history and no receipt returns `RetainedIncomplete` only
when the observed old-or-new feature state validates; this never means rollback.
Different request/hash, newer head, incompatible objects/grants, changed bundle
or inconsistent history blocks reconciliation. No receipt or SQL is synthesized.
Fresh-v1 attempts lack durable history receipts and cannot use this completion
reconciliation path. Attempts are in-memory values; durable outer execution
reporting and a reviewed disposition for a crashed/dirty store remain T-933 or
separate recovery work, not automatic repair in this adapter.

## Fixed policy duplication and boundaries

`persistence.Check` requires a runtime GORM session. Calling it from an owner
pgx session or substituting SET ROLE would violate both interfaces. As explicitly
approved by the coordinator, the driver duplicates the fixed catalog/history
policy inside its owned leaf, evaluating required privileges by the sealed
runtime OID while separately requiring the exact migration current/session user,
database ownership and origin trigger mode. It uses quoted validated identifiers
or parameters, never caller predicate text. The intentional duplication must be
kept aligned when the shared checker gains later approved capabilities.

Checked predicates include exact owner mechanics/default; complete ledger shape;
baseline hashes/references/request; ordered complete stable artifact identities,
manifest/predecessor/feature digests; nonzero unique installation requests,
finite times and provenance; exact marker sets; and enabled unconditional
expected history triggers with expected owner-local invoker functions/search
path. Required ordinary tables must have exact ownership and no RLS. Required
table/column grants are also maximum grants. Direct, PUBLIC, delegated and all
transitive NOINHERIT-role privileges are checked, including database CREATE/TEMP,
foreign owner database access, schema creation, unknown objects, forbidden table
or column writes/REFERENCES/TRIGGER/TRUNCATE/MAINTAIN, sequence/function access,
parameter SET/ALTER SYSTEM authority, and effective built-in/global/additive
schema defaults. Shared mode/lineage markers are exact, separately from private
owner versions. Fresh preflight omits only not-yet-created owner metadata; public
schema usage is allowed before its ledger exists.

Parity probes run the existing runtime checker and the new owner validator
against the same live catalog drift: missing required column grants, broad
UPDATE, PUBLIC SELECT, delegated INSERT columns, reachable NOINHERIT writes,
unsafe function/type defaults and a disabled immutable-history guard. This is
named-object/permission compatibility, not a full constraint dump, administrator
tamper-proof proof, process quiescence proof or business policy authorization.
The trusted outer runner must supply approved profiles, accepted evidence and
quiesced deployment phases. Shared-template psql phases must acquire the key on
their own executing session after this driver's lock is released; no continuous
cross-connection lock claim is made.

Fixture prerequisites explicitly provision owner-global defaults:
`ALTER DEFAULT PRIVILEGES REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC` and
`ALTER DEFAULT PRIVILEGES REVOKE USAGE ON TYPES FROM PUBLIC`.
Original templates remain unchanged and do not establish these defaults.
Fixtures use complete synthetic adjacent manifests, including v1. Actual release
manifests/default provisioning, T-059 schema/profile, T-933 source/CLI, T-934
custody readiness and production baseline acceptance remain separate gates.

## Fix cycle 1 — native asynchronous cleanup after failed integration

The original result above is preserved verbatim. Its candidate passed independent
QA, but coordinator integration `6fecd0d59fba8b6f154b033279d7607560f7045e` failed
the scoped race run at `TestDriverBoundedLockAndPreflight`: `late acquisition
retained lock`. The task was not marked integrated. The original raw log remains
`/private/tmp/justixauto-t932-main-race.log`, SHA-256
`a409332e4bc7eef907b30d1b42c8f4ce0a5e8bae8ce67ba960e1dba86159b585`, also preserved
in main's `qa/integration-t932-attempt1.md` at coordinator commit `3eb1543`.
That old assertion combined observer-query errors with a false lock result; the
raw log alone does not establish which occurred or prove a specific cause.

Investigation found and deterministically reproduced a real close-contract gap.
Pinned pgx v5.11.0 `pgconn.go` marks a failed connection closed before starting
`asyncClose`. That cleanup can wait on its separate CancelRequest dial and drain
for up to fifteen seconds. `Close` returns immediately if the connection is
already marked closed; `IsClosed` explicitly does not prove resource cleanup.
Our original `poison` and `Close` called only native `Close`, so the owned socket
could remain open after the adapter returned a poisoned result.

The new real-server regression drops an actual advisory-acquisition reply, then
holds only native cleanup's separate cancel dial. It does not change PostgreSQL
configuration, terminate sessions, or replace the driver connection with a pool.
Against the original source the regression failed deterministically:
`native IsClosed=true; server={"backend": true, "advisory_locks": 1}`.
This proves an actual retained backend/lock is possible under the original close
implementation. It establishes a defect independently of the ambiguous original
integration observation; it does not retroactively identify that log's exact
branch. Before-fix log: `/private/tmp/justixauto-t932-fix1-before.log`.
Its hashed observation is retained under
`/private/var/folders/yq/j2ffv8bj2f35mcvbk7v7rk3m0000gn/T/justixauto-t932-evidence-781809832/`.

The fix uses only the owned connection's public native API. `closeOwned` performs
native `Close` and also closes `PgConn().Conn()`, ignoring only the normal
already-closed transport result. Both poisoning and ordinary driver Close use
it, and poisoning retains any close error. Concurrent net.Conn.Close is permitted
while native cleanup finishes. No private pgx fields, server-wide setting,
backend termination, extra driver connection or dependency change is involved.
The driver itself issues no future acquisition or SQL after poisoning; native
cancel/terminate cleanup is not migration acquisition work.

The first scoped race run of this fix also exposed an existing fault-fixture
bug: its DialFunc reused `wireFault` for native CancelRequest dialing and
reassigned the primary transport concurrently with closure. This was not an
additional production connection or driver-field mutation; it was a test wrapper
incorrectly conflating two different sockets. The wrapper now sets its primary
transport once under its mutex and returns a separate raw socket for subsequent
native cancel dials. The failed race evidence remains
`/private/tmp/justixauto-t932-fix1-scoped-race.log`; corrected verification is
reported separately. The deterministic retained-lock reproduction uses a
different dedicated wrapper and is independent of this old fixture defect.

Physical client closure does not synchronously prove PostgreSQL has processed
disconnect and released locks. The strengthened contention test keeps its
blocking connection locked while making a separate bounded server observation:
a failed closed driver's backend and advisory locks must disappear within one
second; a known-no-lock poll-timeout connection must be idle with no held lock
or client acquisition work. It then releases the blocker and still requires
immediate successful reacquisition. Observer SQL errors now have a distinct
diagnostic from an actual false acquisition result. Lock's five-second context,
preflight coverage and existing timing assertion are unchanged.

The deterministic regression separately proves transport Close occurred while
the native cancel dial is still blocked, observes bounded backend disappearance,
and immediately reacquires the owner lock from an observer connection. It also
checks no dirty attempt was created. Thus the original test was not merely
replaced with an unbounded retry or a weakened lock assertion. Fresh bounded
reconciliation remains the production mechanism for authoritative server state;
no new claim equates `IsClosed`, socket closure and server release.
