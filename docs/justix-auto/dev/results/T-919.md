## Adapter contract and dependent-task handoff

`NewMessage(envelope, typedSchema, sourcePlanRule)` seals one validated
serialization and SHA-256. `NewCustodyInserter(tx, owner, admissions)` requires
the same underlying SQL transaction as the source admission repository.
Construction performs no SQL. `InsertMessages` takes only sealed messages;
there is no caller destination/subset or cached DeliveryPlan input.

The owner authorizes its emission rule and concrete admissions first. In its
ordinary T-009 typed UnitOfWork, call `SourceAdmissions.Fence` once with **all**
affected streams before any append or other stream locks, append all events,
then call `InsertMessages`. The writer calls Resolve and ValidatePlan inside
that same transaction, immediately before each parent/all-child insertion.
It persists sorted destination/root-admission references and the resolved plan
authority, including an explicit empty-plan authority when no recipient exists.
Missing configuration never means an empty permitted set.

The INSERT SELECT compares actual local event ID, owner, aggregate type/ID,
domain revision, integration position, full type/schema version, company,
occurrence time, actor kind/ID, correlation, causation and operation. The local
event must have been appended by the current SQL transaction. Internal events
and committed historical events cannot be re-planned. Integration payload bytes
are separately schema-approved and need not equal domain-event JSON.

Every recipient receives a delivery row referring to the single stored parent
and its original bytes/hash/event ID. Routes remain exactly
`source.target.fullOwnerQualifiedEventType`, including source-to-self routes.
Each child insertion must affect one row. SQL immutable/completeness constraints
remain a second enforcement boundary. Duplicate IDs/positions, changed metadata,
missing/extra children or any late write failure must be propagated to Run,
which rolls back append, guards, admissions, parent and all children together.
There is no internal transaction, retry, commit, network action, publish or ACK.

A nil error is only an uncommitted transaction candidate. Owner command receipt
and guard writes must share the outer transaction. Any commit error remains
`eventstore.ErrCommitOutcomeUnknown`; reconcile the owner's authoritative
receipt before reporting completion or retrying the command. The writer does
not expose a success receipt or reinterpret unknown as rollback. T-012 retries
the persisted parent bytes and each child's original route/admission; it never
resolves a new recipient set for historical work.

`NewInserter` / `NewRecord` / `Insert` preserve the explicit single-target legacy
API. Calling this API selects legacy mode; custody adapters cannot use it.
Both APIs check mode even on zero input. Checks require read-committed isolation,
take a table lock before reading active mode, reject conflicting transaction
markers, and check installed owner/runtime identity. The original T-008 schema
is accepted only by the legacy API. The custody path requires mode `custody`,
base schema 2 and the exact T-925 singleton owner/runtime, revision 3, route
format 1, artifact hashes, finite install timestamp and nonempty evidence refs.
Its `SET LOCAL justix.messaging_mode='custody'` is a compatibility marker, never
authorization. Missing or corrupt installation fails even for empty input.

Locks fence writes against migration, not external side effects or a universal
lock order. Migration still stops runtimes/channels; lock timeout/deadlock errors
must abort the outer transaction. Full startup ACL, deployment, admission and
broker compatibility checks remain T-022/owner-composition responsibilities.
No business admissions, bootstrap policy or revocation disposition were invented.
