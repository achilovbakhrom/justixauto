## Storage and installation handoff

000004 creates owner-private `consumer_bootstraps`, `consumer_checkpoints`,
`consumer_gaps`, `consumer_gap_attempts`, and the immutable
`projection_checkpoint_compatibility` singleton. No prior rows are imported,
rewritten, reset, deleted or treated as checkpoint zero.

Bootstrap K, kind, generation, request, contract, authority/scope/purpose,
source high-water and snapshot/no-snapshot evidence are immutable. One bootstrap
per K prevents a second request from resetting progress. Zero needs explicit
new-empty proof; a nonzero high-water is required otherwise. In custody mode the
exact root local admission must match K, kind, generation, high-water and
contract/authority evidence. References have validated shape, not intrinsic
business authorization. An exact request replay is reconciled by reading its
retained evidence; INSERT conflicts rather than overwriting it.

Checkpoint insertion must match its complete bootstrap identity and start at
that exact high-water with revision zero and no last event. Updates change only
position/revision by +1 and require a new matching consumer/event/hash inbox row.
An inbox row may be in the same transaction or already committed. Key/bootstrap
fields cannot change; runtime DELETE/TRUNCATE is denied. SQL does not parse an
envelope or establish that this inbox event belongs to S and this position:
T-014 must validate and seal that evidence before the update. It must also
preserve the immutable meaning of a consumer name across its stream universe.

Gaps retain blocked identity/hash and exact K/bootstrap. Attempts have one root
per gap, one successor per predecessor, same-gap checks and immutable request
identity. Existing-parent foreign keys plus immutability prevent cycles;
uniqueness rejects concurrent roots or forks. Intervals stay within the gap's
missing range, and resulting progress matches the authoritative checkpoint.
Recovered attempts require manifest reference/hash; held attempts require a safe
bounded reason code. A gap resolves only after its missing interval is covered;
a stale hold cannot be appended once coverage is observed. Current-tip selection,
authority validation and cooperating receiver fences remain adapter duties.

## Typed lock preparation handoff

`SourceFence`, `ReceiverFence`, `GenerationFence` and `GuardFence` construct
opaque immutable declarations. Source requests are explicit T-009 prerequisites;
the helper acquires them first using the exact existing append keys. It then
takes shared/exclusive owner catalog, sorted exclusive receiver streams, and
sorted generation/guard keys. Duplicate declarations merge to exclusive before
acquisition. Generation/guard components use UTF-8 byte-length prefixes, avoiding
delimiter aliases. Guard scope mapping remains the approved owner's contract.

`PrepareFences(ctx, tx, owner, catalogMode, requests...)` binds one complete set
to the actual outer ReadCommitted PostgreSQL transaction. Server transaction ID,
backend identity and a transaction-local nonce are checked before and after
acquisition. A committer-shaped pool, ended transaction or second preparation
fails. No late shared-to-exclusive upgrade is allowed. This API performs no
DDL, nested Run, commit, broker ACK or external callback.

`PreparedFences.Require` checks the same live transaction, owner, catalog mode
and every required key/mode before an adapter reads/writes its effect. A copied
capability or cloned GORM session does not widen coverage. Missing prerequisites
require rollback and replanning outside the transaction. T-014/920/921/923 and
owner compositions must actually use this check and declare their full write
set before head/job/inbox/checkpoint/effect locks. Advisory locks are cooperation
inside a trusted owner service, not discovery of uncooperative writers or user
authorization. The helper adds no automatic retry/deadlock-free global claim.
