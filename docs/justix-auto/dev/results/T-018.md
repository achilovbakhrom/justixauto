`Operations[I,R,E]` is constructed in the T-009 adapter factory alongside typed
owner ports bound to the same SQL transaction. Creation belongs with initiating
events, guards, T-017 receipt and T-011 outbound work; subscribers bind it with
T-013 inbox and their next local effects. Every adapter error must abort the UOW.
Returned snapshots/claims/results remain candidates until commit succeeds.
There is no DB getter or application callback receiving a SQL handle.

`OperationPolicy` requires an owner-declared nonsecret typed input projection,
safe result/error validators, exact phase/terminal catalog, initial admission
validator and transition validator. There are no default business states.
Initial records are undecided and nonterminal. Advance locks the owner/kind row,
checks string expected revision, terminal state, immutable commit/abort choice,
safe DTOs and owner transition policy. It is an internal owner command port,
not an administrative status setter. The unchanged SQL trigger independently
prevents reversing a decision. Owner code must enforce live domain guards.

`Steps[I,R]` binds an approved kind and stable step name with its own typed
request/result schema. `(operationId,step)` serializes on the operation row;
matching normalized digest replays the validated stored result, changed input
returns existing `ErrConflict` (HTTP409), and malformed stored outcomes fail
closed. Completed steps and local effects commit atomically. No raw request,
credential or arbitrary transport error is stored. Input schemas must omit
secrets; credential-specific schema registration is rejected here. These
technical validators supplement, rather than replace, owner PII allowlists.

Status and resume apply exact company/kind filtering in SQL before a required
fresh actor/action authorization callback. That owner callback checks current
branch/party scope and operation-manager rights; same-company membership alone
does not grant access. Status reads the authoritative owner ledger. Resume only
makes the retained nonterminal operation due: it does not change decisions,
phase, receipts, attempts, attention or an active lease. No override/delete API
exists. HTTP handlers and exact public DTO/error mapping remain owner tasks.

Claim uses due nonterminal rows with `FOR UPDATE SKIP LOCKED` and a new UUID
fence per acquisition. A worker uses the retained operation ID and stable step
for remote requests. `WithClaim` locks the row and checks the current token and
database lease time in a fresh statement before local effects; stale workers
cannot commit through it. Long remote calls happen outside this local UOW;
remote owners must deduplicate and provide authoritative receipts. Successful
local work releases the same scheduling fence. Leases never expire a hold,
choose abort, or undo commit. There is no terminal timeout/TTL.

Retry delay is exponential with bounded jitter, always 1–60 seconds, including
maximum bigint attempts. The composition root supplies randomness and lease
duration. Retry changes scheduling metadata only; it never maps a timeout to a
business error. Claim/retry mark attention after five minutes. `MarkAttention`
also scans aged nonterminal operations with live leases or future retry dates.
Its mandatory callback persists an alert/outbox intent in the same UOW; alert
failure rolls back the flag. Concurrent scanners serialize, and flagged rows
do not duplicate the transition intent. Actual alert transport is downstream.

The composition root must periodically call Claim and MarkAttention. This task
provides bounded durable scanner/claim primitives, not a daemon or operational
polling SLA. Exact owner protocols, periodic wiring, alerts, authorized remote
step preparation and admission are downstream composition responsibilities.
No fan-out or subscription activation was added; T-011's single-target outbox
constraint remains. No broker delivery or cross-owner atomicity is claimed.
