## Storage and adapter handoff

`quarantine_evidence` is immutable and keyed by a separate evidence UUID and
unique capture request UUID. It stores stage, exact local owner, trusted queue
or consumer/stream context, optional trusted custody job identity/observation,
raw SHA-256 and byte length, sealed ciphertext and its checked SHA-256, required
format/key/capture-policy references, a bounded ASCII reason code, trusted
capture-context digest, and finite capture time. Empty or arbitrary malformed
raw input has no event-ID requirement. There is no raw-body, free-form error,
untrusted claimed-event-ID or arbitrary JSON column. Claimed IDs stay inside the
protected input. Equal bodies in different contexts are separate evidence;
request reuse conflicts instead of overwriting anything.

SQL verifies ciphertext digest and required shape. It cannot establish that
content was encrypted or that a raw digest is cryptographically bound to the
seal. T-015's mandatory owner security port must produce that binding outside
the SQL transaction using an accepted policy/key adapter. Missing sealing or
policy must fail closed before any ACK. No production cipher, key, byte limit,
retention schedule, purge or plaintext fallback is supplied by this leaf.

For `custody-handler`, the insert guard compares exact consumer/job identity,
source stream, retained envelope hash/length and the current unfinished/completed
observation against the existing dispatch rows. It performs invoker reads, adds
no triggers or foreign keys to old tables, and does not acquire earlier-order
locks. The outer adapter must prepare the complete fences, lock and recheck the
same live job and lease, and atomically insert evidence/actions plus its exact
`quarantine:<evidence UUID>` job reference in a fresh transaction after the
failed effect transaction rolled back. A completed observation can be retained
without reopening or quarantining the job. SQL does not automatically set a
reference, invent an inbox row or advance a checkpoint.

`quarantine_actions` is append-only with one root per evidence, a unique
successor per prior action, same-evidence predecessor checks and unique request
identity. Existing-predecessor checks plus immutable rows prevent cycles;
concurrent forks conflict. Actions are `hold`, `redrive-request` and
`redrive-result`; their evidence version is exactly 1. Actor, authority, scope,
purpose, repair, intended path/consumer, checked manifest reference/hash and
finite time are retained. References and supplied manifest digests are typed
adapter evidence, not SQL authorization or validation of external content.

A result requires its exact preceding request's authority and target context.
Accepted results require the matching retained authoritative receipt:

- `inbox` for the exact direct consumer, event and hash;
- `custody` for the intake event/hash, meaning durable custody only;
- `job` for the exact completed consumer/job and matching inbox hash.

No result record supplies absent progress or turns an unfinished job into a
completed effect. Custody evidence cannot target another consumer obligation.
Held, requested, denied, failed, accepted and released outcomes have explicit
action-specific shapes. A released result is audit evidence, not an effect
receipt; the outer adapter must atomically release only its own reference while
preserving other holds. Current-tip/fence checks, redrive authorization before
plaintext restoration, original hash/length validation, ordinary intake/dedup,
source-authorized corrections and post-application crash reconciliation remain
T-015 and its ordinary intake/dispatch composition responsibilities. No source
event ID or integration position is fabricated by this migration.

## Installation and privilege boundary

Required psql variables are `owner_service`, `runtime_role`,
`base_schema_sha256`, `prior_migration_sha256` (000002),
`correction_migration_sha256` (000003), `checkpoint_migration_sha256` (000004),
`quarantine_migration_sha256` (this artifact), `backup_ref`,
`stopped_runtimes_ref` and `compatibility_ref`.

The script uses an explicit BEGIN/COMMIT, search path `pg_catalog` and five-second
lock waits. It checks migration ownership, runtime identity/privileges, all exact
preceding digests and installed owner/runtime/revision/format lineage, owner
default and prerequisite function properties. Locks take outbox, inbox, mode,
messaging parents/children, then remaining prerequisites in stable name order.
Wrong identity/artifact, existing marker, incompatible grants or lock contention
rolls back the entire installation. The runner must verify actual files and
backup/stopped-process evidence; SQL cannot hash its own input or attest those
external facts.

The immutable `quarantine_compatibility` singleton is revision 5, feature format
1, with complete preceding artifact identities and its supplied exact digest.
Base messaging schema version remains 2 and its legacy/custody mode is untouched.
Existing rows, table/column ACLs, owners, OIDs, trigger attachments, functions and
markers remain unchanged. No old references are reinterpreted, imported or
cleared. New evidence starts empty.

Runtime grants are SELECT+INSERT on the two append-only tables and SELECT-only
on the marker. UPDATE/DELETE/TRUNCATE is denied; invoker immutable triggers also
reject ordinary migration-role DML and TRUNCATE. A trusted database owner can
still deliberately alter DDL: this is not tamper-proof storage. No SECURITY
DEFINER or callable migration API is added. Audits cover missing required reads,
inserts and schema usage; table/column/PUBLIC/default/delegable privileges;
database CREATE/TEMP; schema CREATE; migration execution; table ownership; and
MEMBER-reachable roles, including a two-hop NOINHERIT chain.
