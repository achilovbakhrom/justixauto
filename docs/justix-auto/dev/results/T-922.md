## API handoff to T-923

`NewTransactionalConsumer[U](tx, name, bind, validate)` is constructed by an
outer persistence adapter using its already-open transaction. `bind(tx)` supplies
the owner's typed effect/checkpoint ports. Bind every job/effect/checkpoint
repository to that same transaction; factories only construct local adapters.
The adapter has no runner, commit method or ACK callback. Plain pools and invalid
handles are rejected, and use of a committed/rolled-back handle fails at SQL.
Owner domain/app/port packages must remain independent of GORM and this adapter
package; map mechanics to owner-declared typed ports in the outer adapter.

`Apply(ctx, body, apply)` clones the raw received bytes, structurally decodes the
envelope and calls the mandatory subscribed-schema/source/scope validator before
every lookup, including duplicates. The existing exact SHA-256 identity check
and `(consumer_name,event_id)` SQL conflict serialization are shared with the
direct path. The typed callback receives only U and the immutable envelope.
It must enforce the owner's sequence/admission invariants, persist only local
effects/checkpoints/outbox intent, and return errors without swallowing them.

The return type is **Candidate**, distinct from the existing committed Outcome:

- `AppliedCandidate`: inbox and effect/checkpoint are staged in this transaction.
- `DuplicateCandidate`: identical inbox evidence exists; the effect callback did
  not run. This includes retained pre-migration inbox entries.
- `NoCandidate`: validation, mode, SQL, identity or callback failure.

Neither nonzero candidate is a committed receipt. The caller must complete its
own pending job for either candidate in the same outer transaction. In T-923,
lock/fence the exact job and lease before invoking Apply; require the final
lease-conditioned completion write afterward, returning an error if it loses the
fence. An old inbox can therefore complete its pending migrated job without
reapplying effects. Never complete another consumer's job or infer its checkpoint.
The candidate and transaction-bound ports must not escape that transaction.

Propagate every error to the outer `eventstore.Transactions.Run`; do not nest Run
or commit/ACK inside Apply. Only successful outer commit can become a committed
local result. Discard candidates on rollback or `ErrCommitOutcomeUnknown`;
reconcile durable inbox AND job completion on unknown commit, including when the
candidate was Duplicate. The primitive never retries callbacks automatically.

## Mode and locking limits

`NewConsumer/Consume` retain the original single-consumer direct-ACK signatures,
post-confirmed-commit ACK, exact-duplicate behavior and Unconfirmed error outcome.
Calling Consume explicitly selects the legacy single-consumer composition.
It accepts the original T-008 installation, or the installed T-917 schema while
mode is legacy. Installed custody mode rejects both fresh and duplicate direct
calls before their effect or ACK, even if the connection has a custody marker.

The new caller-transaction Apply requires installed T-917 schema version 2 in
custody mode. Both paths require ReadCommitted, so the duplicate hash read sees
the fresh statement snapshot after a concurrent insert commits. RepeatableRead
and Serializable are rejected rather than weakening this assumption. An existing
incompatible transaction marker is rejected. Custody Apply sets
`SET LOCAL justix.messaging_mode='custody'` for the SQL inbox trigger; this is a
compatibility marker, never authority, and does not leak through pooled sessions.

Before reading mode, Apply locks `eventstore.inbox` in ROW EXCLUSIVE mode until
outer transaction end. The narrow runtime already has the required INSERT
privilege; its SELECT-only messaging_mode grant is unchanged. This table lock
fences even duplicates against the cutover's ACCESS EXCLUSIVE inbox lock.

This does **not** establish a global lock order. Cutover locks legacy outbox
before inbox; an effect that already holds inbox and then requests outbox can
contend with an improperly concurrent migration. A live test explicitly
reproduces that inversion and obtains PostgreSQL lock timeout `55P03`: inbox,
effect and checkpoint all roll back, no ACK occurs, cutover subsequently succeeds,
and later direct calls reject the new mode. No automatic retry or success follows
that failure. The approved requirement to stop old writers/consumers and close
their delivery channels before cutover remains necessary, including the gap
between database commit and post-commit broker ACK.

T-923 must consistently order job/lease acquisition before this inbox/effect
boundary and use the approved sorted stream locks within owner effects; any
other cooperating path must respect that order. A job lock acquired by an outer
dispatcher is outside this helper's control. Migration/maintenance must exclude
running dispatchers and follow its own documented global lock order. Propagate
deadlocks and timeouts through the outer transaction rather than claiming this
helper prevents every cross-adapter cycle. No extra privileges were introduced
to acquire a messaging_mode row lock.
