## Internal model and activation boundary

The existing compiler recognizes document `x-justix-auth-semantics: 1` paired
with operation `x-justix-auth-transport: 1`, only for public Identity routes in
the adopted ten-operation T-058/P4 matrix. Wrong/missing versions, owners,
internal markers, orphan semantics, missing marked auth operations, unsupported
routes/methods/statuses, wrong success statuses and missing anonymous session 401
fail. Existing schema/parameter/reference/namespace/security checks still run.

Auth response headers require exact canonical names, inline Header Objects,
`required:true`, optional string description, and the closed schema forms approved
in the [2026-09-16 serialization refinement](../../state/approvals/auth-transport-compatibility.md):

| Header | Exact schema |
|---|---|
| X-CSRF-Token | `{type:"string",pattern:"^[A-Za-z0-9_-]{1,4096}$"}` |
| Retry-After | `{type:"integer",minimum:0,maximum:2147483647}` |
| Cache-Control | `{type:"string",const:"no-store"}` |

Every auth response declares Cache-Control; CSRF declarations exactly match the
route/status rotation matrix, and Retry-After appears exactly on declared 429.
Missing or forbidden headers, casing aliases, extra keywords, references, nullable
or alternate encodings reject. The bounded integer schema represents Retry-After's
value; the canonical decimal wire pattern `^(0|[1-9][0-9]{0,9})$` and maximum
2147483647 are explicit immutable internal metadata. No general header-schema
equivalence or new rate/security policy is inferred.

Unsafe auth operations require exactly one canonical request CSRF header with
the same schema. Its preserved declaration lives at
`operation.authTransport.requestCSRF`; it is deliberately excluded from ordinary
`operation.parameters` and the generated parameter schema's properties/required
set. Safe GET and internal/non-auth CSRF declarations reject. T-058 explicitly
forbids auth handshake If-Match and Idempotency-Key declarations; non-auth endpoints
retain their existing supported headers. Other ordinary path/query parameters
retain their existing validation and representation.

The auth plan has `authProfile:{version:1,semantics:1}` and each marked operation
has frozen `authTransport:{version:1,semantics:1,requestCSRF,metadata}`. Per-status
metadata records required/forbidden CSRF and retry directives, no-store, cloned
header declarations and the retry wire grammar where applicable. Header and auth
security metadata are deep snapshots and frozen; input mutation cannot change
them. Existing cookie/mutualTLS scheme validation is preserved, including named
scheme resolution and explicitly declared anonymous alternatives. This does not
invent cookie presence/authorization or replace owner checks.

**Public auth generation remains unconditionally rejected.** Main rejects the
compiled marked plan before rendering/output planning; both private renderer
entry points independently reject it too. There is no exported auth compiler,
environment switch, config switch, CLI switch, partial auth output or advertised
transport capability. No concrete auth config entry is registered. T-938–T-941
still own semantic/runtime/rendering work, with terminal activation only at T-942.

Legacy documents have no new auth model fields. Valid non-auth/internal output
bytes and signatures remain unchanged. Existing cookie security metadata alone
retains its historical behavior; it does not advertise the new auth response
profile or concrete authentication semantics.
