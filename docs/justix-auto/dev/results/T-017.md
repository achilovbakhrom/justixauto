`NewLedger[I,O]` binds the same SQL transaction as an owner's event/guard/outbox
ports inside T-009's typed UnitOfWork factory. Application code consumes its own
ports; the shared adapter exposes no database getter. `Execute` takes actor,
company, target and UUID key plus an owner-declared command schema. It acquires
a transaction-scoped advisory lock for the complete key, then reads the real
receipt. Matching inputs replay that outcome; changed inputs return generic409.
The immutable SQL unique constraint remains the second concurrency fence.
Effects and receipts commit or roll back together. Every error must propagate to
the outer UnitOfWork; returned candidates must not be sent before commit succeeds.
No network/broker effects belong in the callback.

The adapter trusts the composition root to bind the appropriate owner database.
Scope values must come from freshly authorized context, and feature command
ports own branch/party/state/invariant and expected-revision enforcement. A human
retry reauthorizes before entering the ledger; recovery rechecks actor/company/
action scope. No authorization, finance policy or business uniqueness is inferred.

`Schema[I,O]` requires explicit owner normalization and safe result validation.
Normalization retains all effect-affecting nonsecret fields and preconditions.
Encoding passes its typed JSON projection through an object model with
`UseNumber`, then deterministic Go JSON object-key encoding. Null and omitted
are distinct; array order and exact decimal strings are retained. Numeric
`json.Number` spellings require owner normalization. This is not RFC8785.
Changing projection/normalization is a versioned command compatibility decision.
The ledger stores only a 32-byte digest and safe outcome, never the input body.

Identity provisioning uses `NewSecretSafeSchema`: copied configuration key,
HMAC-SHA256 of normalized NONSECRET input, and a required private credential
retry verifier. No supplied password/password hash is passed to the ledger.
The verifier checks the created credential through owner-private ports without
resetting it. Mismatch returns409; dependency errors remain errors rather than
pretending that a password mismatched. Later credential change can make replay
unavailable. Key rotation/retention belongs to owner configuration: the approved
table has no key-version column, and this task invents no rotation policy.

`Recover` reads the authoritative owner database without requiring the old
password. Missing receipt is not proof of rollback while a transaction is in
flight. Both actual-commit/lost-reply and actual-rollback/lost-reply return T-009's
unknown-outcome error; authoritative recovery and identical retry converge to one
committed effect. Do not use a projection/read replica for this recovery API.

Receipt DTOs must be owner-declared safe allowlists carrying affected IDs/state
and related object string revisions. The shared recursive secret-key check is
defense in depth, not a universal PII detector. Authentication handshakes, MFA
enrollment/verification and recovery responses must never register a business
command schema. No such schemas or auth responses are implemented here.
PostgreSQL JSONB may change insignificant wire whitespace/property order on
replay; the validated typed outcome and HTTP status remain identical.
