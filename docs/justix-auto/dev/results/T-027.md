## Behavior and ownership

- Infrastructure-free generic typed UnitOfWork and Readiness/Dependencies ports.
- Inert PostgreSQL UOW constructor delegates the approved shared ReadCommitted
  transaction mechanism. Read-only compatibility runs before repository binding
  on every Run and explicitly at startup; no automatic migrations or retries.
- Retail-owned version1 migration checks its private database/login, shared
  owner default and dirty single-row ledger before creating runtime-readable
  Retail mechanics metadata. No business tables or service roots are introduced.
- Runtime readiness requires the exact Retail role/database, clean version1,
  marker/default, required grants and narrow maximum direct/column/reachable
  privileges. Wrong owners/ledgers, grants and custody activation fail closed
  before the feature factory/callback. Additive shared legacy mode is supported.
- Tests compose Retail-bound append/load/replay, scoped command receipts and
  operation state through concrete synthetic ports. Real commits, rollback,
  panic/cancellation, concurrent replay/idempotency and lost actual commit or
  rollback replies are exercised with authoritative receipt reconciliation.

This follows integrated T-026's reviewed typed scaffold mechanics, with Retail
owner identities and Retail resource-admission commentary. It copies no trading
code, credentials or production policy. Feature commands still admit actor,
company, branch, customer/vehicle and action authority. Company scoping alone
does not authorize resources. The generic transaction port cannot enforce that
a trusted feature factory avoids captured pools/network effects; composition
must bind its repositories exclusively to the supplied transaction.

## Migration and compatibility handoff

Explicitly provision the private Retail migration owner/database and narrow
runtime, install unchanged shared schema.sql with owner_service=retail and
runtime_role=justix_retail_runtime, mark owner version1 dirty, execute the entire
0001 SQL, and mark clean only after known success. Runtime receives metadata
SELECT/schema USAGE only. Fixtures implement this explicit SQL protocol; they
do not execute or claim the future owner migration driver/runner.

This constructor remains legacy mechanics-only, matching the approved scaffold.
T-930's newly integrated exact profiles are not silently bound to Retail here;
later Retail root compatibility/profile follow-up, complete adjacent baseline
manifests/default provisioning and custody support remain explicitly gated by
owner-migration-readiness.md and the existing owner-root task. No arbitrary
newer head, destructive down, automatic repair, business feature, production
baseline attestation, HTTP server or broker worker is implemented.
