## Storage and dependent adapter handoff

`projection_generations` is immutable, keyed by projection name and nonzero
generation UUID. Consumer names are globally unique within this owner-local
generation registry and cannot be recycled after abandonment. Only projection
kind is accepted. Handler/contract identities, format 1, authority/scope/purpose,
history and bootstrap manifest references with 32-byte hashes, unique creation
request UUID and finite creation time are retained. This introduces no business
read model or process historical-replay API. Retained process generation labels
remain exact nonempty text in their existing tables.

`projection_generation_events` retains one immutable root per generation and at
most one successor per predecessor. Foreign, absent, self and abandoned
predecessors fail; immutable rows and existing-parent checks prevent cycles.
Unique request UUIDs allow exact fresh-read reconciliation. Build progress,
validation, hold, abandonment and switch have versioned shapes, source-vector
and historical-cursor manifests/hashes. Validation must follow a build observation
at its exact vector/cursor. A switch must follow passing validation at exactly
the same vector/cursor and comparator ID/version/result/reference/hash. Failed
comparison remains evidence and cannot become a switch receipt. Hold/abandonment
requires an explicit nonempty hold reference; abandonment is terminal for that
generation's evidence chain.

SQL checks shape, equality and identity. It does not retrieve referenced manifests,
prove that their supplied hashes match external contents, compare stream-vector
dominance, grant history authority or certify a business comparator. T-016 must
seal canonical manifests and revalidate current complete stream universe,
admissions/holds, contiguous checkpoints and unresolved gaps under the approved
fences. Stored custody and the presence of a supplied hash are not authorization.

`projection_heads` starts inactive at epoch 1, with no active generation, hold or
event references. Every update advances exactly one epoch and references new
immutable switch/active-hold evidence whose expected old epoch and old generation
match the locked head. A switch chooses the evidence's same-projection target,
rejects a same-active-generation no-op, records its switch event and clears the
hold. An active hold retains that generation and prior switch event while naming
its own evidence. `last_event_id` supplements `last_switch_event_id` so a hold
does not erase the switch identity. The only UPDATE grants are active generation,
epoch, hold reference, those two event IDs and finite update time. Identity
updates, deletion and truncation are prohibited.

A deferred constraint trigger additionally requires each switch or active-hold
receipt to match the final head state before commit. A zero-row stale CAS cannot
leave a falsely committed switch receipt. A hold on the active generation also
cannot omit its expected pointer fields and masquerade as an inactive hold.
This bounded protocol supports **one
head change per projection per transaction**; multiple changes in one transaction
fail closed. Hold release is represented by a valid switch here, not an invented
resume action. Any dependent need for a different transition must be reviewed
before extending this state shape. An inactive-generation hold can remain an
event with no head change or expected pointer.

The outer adapter acquires the complete catalog/receiver/generation/guard fences
before the head and effect rows; triggers do not acquire earlier-order locks.
Read-row batch writes and cursor events belong in one actual owner transaction;
the final comparator/switch/CAS belongs in one transaction. Unknown outcomes
discard candidates and reconcile the exact stable request, generation, expected
pointer and evidence from a fresh authoritative read, including subsequent head
history. No callback retry or missing-reply success inference is supplied here.
Previous generations, evidence and obligations remain retained. Actual reader
generation/epoch pinning and cross-request pagination belong to T-016/owner query
ports. No rows are deleted or consumers implicitly cancelled on switch.

The installation preflight now rejects effective SET **or ALTER SYSTEM**
permission on `session_replication_role` through the runtime, PUBLIC or any
MEMBER-reachable role, including two-hop NOINHERIT paths. It also rejects an
already non-origin installer session and applicable role/database startup

revokes a deployment grant or resets a mode. This closes a demonstrated ordinary
runtime trigger/FK bypass, not a claim against trusted owner DDL. Future readiness
must continue checking this authority and the fixed enabled/invoker trigger
properties; post-install administrator privilege changes are not prevented by
a historical migration marker.

Deferred constraint triggers are no longer assumed to run only at commit.
They can run at caller-selected times. In addition to the deferred backstop,
every relevant immediate mutation now checks actual transaction provenance:

- `projection_generation_events.created_xid` is `xid8 NOT NULL`. The fixed
  invoker INSERT guard always replaces a supplied value with
  `pg_current_xact_id()`, the actual top-level PostgreSQL transaction ID.
- `projection_heads.last_mutation_xid` is nullable `xid8`. Initial INSERT always
  replaces a supplied value with NULL; it does not spend the first pointer
  change. Every UPDATE assigns the actual top-level transaction ID and rejects
  an old row already mutated by that transaction.
- Head changes require evidence inserted by that same actual transaction. A
  switch also rejects this transaction's inactive hold on its target, even if
  the caller already flushed that hold's constraint. Conversely, inserting a
  purported inactive hold on a now-active generation fails immediately.
- The deferred receipt check retains exact event/epoch/generation/hold matching
  and also matches event and head transaction provenance. Immediate mutation
  checks prevent later writes from invalidating a successfully flushed check.

Neither bookkeeping column has a runtime UPDATE grant; event rows remain
immutable. Existing table INSERT grants allow explicitly supplied values, but
the fixed invoker guards overwrite them before storage. Tests demonstrate both
overwriting and denied direct UPDATE. These fields are local transaction
bookkeeping, **not caller intent, comparator identity, authorization, business
event content or a durable receipt substitute**. T-016 must omit them from
caller-intent hashes/manifest comparison and use exact immutable request/evidence
for unknown-outcome reconciliation. T-934 must recognize their exact types and
grants in revision-6 compatibility checks. They use server xid8 values directly,
without caller GUCs, xmin/subtransaction inference or client-generated IDs.

Using the actual top-level ID covers released savepoints. Transactional rows
also make rollback correct: ROLLBACK TO removes inserted evidence and restores
the previous head provenance, permitting one later mutation. Full rollback
similarly does not consume future work. Fresh generation/head construction and
first activation in one transaction remain valid. Legitimate separate-transaction
head changes and an inactive hold committed in an earlier transaction remain
valid; this is not a permanent ban on selecting previously held generations.
The existing hold/switch business action catalog is unchanged.
