## Implemented contract

`NewRelayStore` is an inert outer adapter for an explicit `RelayLegacy` or
`RelayCustody` mode and standard private owner database/runtime identity.
`Check` and every operation inspect mode under the existing migration table
fence. Original T-008 legacy and additive legacy are supported; custody requires
the immutable T-925 revision-3 / format-1 marker and its exact artifact hashes.
There is no automatic migration, mode activation, admission lookup or recipient
replanning. Construction rejects a caller SQL transaction.

Readiness rejects foreign owner identity, privileged reachable roles including
NOINHERIT chains, database CREATE/TEMPORARY and public/eventstore schema CREATE,
missing required SELECT or scheduling UPDATE, broad/column mutation of retained
bytes, REFERENCES/MAINTAIN/destructive privileges, and grant delegation on the
tables this relay consumes. Installed mode/route metadata must also reject
table/column INSERT and all UPDATE. These are relay compatibility checks, not
the future owner feature-migration readiness profile or a general database audit.

`Claim` locks one due recipient with `FOR UPDATE SKIP LOCKED`, increments its
attempt counter, assigns a fresh UUID token and bounded lease, and commits
before any AMQP call. Legacy claims retain the single exact target. Custody
claims join the immutable message to its retained destination row. The relay
verifies retained envelope identity/stream/sequence/hash and exact
`source.target.fullOwnerQualifiedEventType` route, without reserializing or
looking up current aggregate state or current schemas/admissions. An explicit
empty parent plan produces no publication.

`Publication` and `RelayLease` seal original bytes, route, event ID, issuing store
and attempt. Byte accessors copy. An unknown claim commit returns a reconciliation
handle with **no publish authority**; the real publisher rejects it before dial.
`Reconcile` reports durable missing/pending/leased/held/sent state after checking
the retained identity. It does not promote unknown claims, replay work or renew
leases. A fresh claim after expiry is required. Every commit error is conservatively
`ErrRelayUnknown`, including an injected reply lost after actual server commit.

`Relay.Once` performs one claim, a pre-publication lease/hold recheck, one bounded
publication, and a separate conditional completion. `Retry` changes scheduling
only, using persisted attempt counts for the architecture's exponential 1s→60s
backoff with bounded jitter. The first delay is exactly one second; subsequent
delays sample the upper half of the capped exponential interval, never below
one second or above sixty seconds, matching the existing operation-worker
convention without introducing a cross-package dependency. `MarkSent` needs
the sealed routed-confirm receipt for that exact attempt,
then locks the row and performs a final **current database clock** check of the
non-NULL, unexpired token and absence of a hold. Waiting behind another writer
cannot reuse a pre-wait clock observation. Expired, missing, held, foreign or
stale ownership changes zero rows. Sent rows cannot be reset through this API.

`AMQPPublisher` owns one fresh, non-recovering connection/channel per attempt;
the injected dialer must honor context through TCP/TLS/AMQP negotiation and
return a dedicated connection using the owner relay credential. It rejects
client automatic recovery. It makes no declarations, bindings, queue reads or
credential/topology changes. Each attempt uses persistent mode, mandatory
routing, the exact retained event ID and bytes, and an explicitly enabled
confirmation channel. Context/lease deadlines close the owned connection.
Next scheduled attempts reconnect from scratch; no stale channel sequence is
reused. This deliberately favors simple correlation over connection reuse.

Only one publication is outstanding on a channel. A return is matched against
message ID, exchange, route and bytes; a confirm must match its sequence. The
ACK branch drains any buffered return before accepting success, because Go
select order is not AMQP wire order. Returns, NACKs, timeout, wrong correlation
and channel loss produce no routed receipt. Dial/channel errors do not expose
injected URLs, passwords or payloads. The pinned client dispatch behavior and
[RabbitMQ confirmation contract](https://www.rabbitmq.com/docs/confirms)
support this return-before-confirm handling.

## Limits and handoff

No contract/storage blocker was found in the assigned scope. Scheduling caps
(lease 1 ms–5 min, AMQP attempt 1 ms–1 min) are technical bounds,
not business expiry/cancellation rules. There is no global publication ordering,
automatic callback retry, automatic recipient activation, consumer/business
receipt, exactly-once delivery or external side-effect protection from a SQL
lease. Local time only bounds networking; PostgreSQL decides completion validity.
A hold cannot recall bytes already in flight. Single-node fixture restart does
not prove multi-node quorum failover or production cutover.

Checked-in T-924 business activation remains empty. Real compositions must
separately supply approved route metadata, audited bindings, narrow injected
relay credentials, owner/recipient admission and release authorization, TLS and
context-aware dialing, migration readiness, and deliberate shutdown/channel
fencing. A routed confirm proves broker routing/persistence for that publication,
not that its intended recipient topology was independently audited or that a
consumer effect occurred. Later intake/inbox/checkpoint/dispatcher tasks and
T-591 retain their acceptance responsibilities. No money, legal, identity,
recovery, PII-retention or product-policy gate is answered by these mechanics.
T-020 and owner composition still own outbox-age metrics and the five-minute
unresolved-work alert. That query must include held/unsent children and use
the immutable parent creation timestamp in custody mode; no relay retry threshold
turns a pending delivery into business failure or cancellation.
