## Explicit migration contract for T-022

The tested two-stage protocol preserves the unchanged shared psql template:

1. Provision `justix_inventory` owner/database through T-005 and separately
   provision unprivileged `justix_inventory_runtime` with only database CONNECT.
2. As `justix_inventory` on that database, explicitly execute
   `pkg/eventstore/schema.sql` using psql `-X`, `ON_ERROR_STOP=1`,
   `owner_service=inventory`, `runtime_role=justix_inventory_runtime`.
3. The future versioned runner uses the same migration login/database and
   `public.schema_migrations` with bigint version and boolean dirty columns.
   Record the single `(1,true)` row before executing the full owner migration,
   including its BEGIN/COMMIT. Mark `(1,false)` only after success. The directory
   is `services/inventory/migrations`.
4. Application composition uses only the narrow runtime login and explicitly
   calls Check before activation. Runtime receives schema USAGE and marker/
   ledger SELECT, with no migration writes.

The test fixture implements this ledger protocol through SQL. No actual
golang-migrate binary/driver or T-022 runner exists or is claimed tested here.
There is no automatic startup migration, destructive down migration, silent
reinstallation or forced clean ledger. Migration metadata is trusted as
owner-controlled; this is not defense against a malicious migration administrator.

The integrated T-917 additive schema remains compatible while in legacy mode.
The fixture then explicitly activates custody with synthetic cutover evidence,
no legacy outbox rows and no running consumers/broker. Revoked old outbox writes
make Check and Run reject before feature binding. This adapter neither installs
nor activates that schema and provides no custody runtime support. Future
T-581 wiring remains gated by the approved messaging amendment and must
explicitly advance compatibility; the marker is not a delivery guarantee.
