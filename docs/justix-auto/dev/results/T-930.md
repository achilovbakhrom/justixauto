`NewProfile` is inert and accepts only the seven exact owner/database/runtime
identities, format/history revision 1, a complete strictly increasing private
artifact sequence beginning at unchanged mechanics 1, exact head, nonzero byte
hashes and stable manifest identities. Numeric gaps are permitted only in that
explicit sequence. The filename version must agree with its artifact version.
Prerequisites must refer to exact earlier identities and include the immediate
predecessor. Each subsequent artifact has one exact feature marker; duplicate
ID/revision keys, absent feature contracts, duplicate tables, reserved/shared
namespaces, contradictory broad/column grants and malformed references fail.
Shared artifacts form their separate explicit ordered revision sequence.

Construction manually deep-copies input, preserving invalid UTF-8 for validation
instead of silently repairing it through JSON. Set ordering and empty sets are
canonicalized for the profile SHA-256. `Specification()` returns another deep
copy; callers cannot mutate feature pointers, prerequisite/grant slices, baseline
or shared hashes through either input or output. A zero profile is invalid.

`ArtifactManifest` is the producer-owned adjacent `.manifest.json` format:
`format_revision`, `owner`, `artifact`, `prerequisites`, `feature_contract`.
Its typed nested identities use the exported Go identity fields and 32-byte
digest values. The file excludes its own digest and any installing bundle or
request identity. The trusted profile records the original manifest-byte digest.
`VerifyFiles` requires an explicit absolute trusted owner directory, walks every
root/path component with `Lstat`, rejects regular/dangling/directory symlinks,
escapes and nonregular leaves, and rehashes ALL private SQL and adjacent manifest
bytes, including already installed lower versions. It additionally rejects
unknown/trailing manifest fields/data and mismatched typed owner/artifact/
prerequisite/feature identity. Shared/template verification belongs to the
explicit outer runner. No filesystem mutation or hostile concurrent filesystem
fencing is claimed: the future runner must retain verified bytes and rehash after
its reader boundary. Runtime readiness never scans files or selects its own head.

## Read-only readiness and limits

`Check` uses only SELECTs on the supplied GORM handle and caller context. It opens
no transaction, binds no repositories, retries nothing and accepts no caller SQL
or readiness callback. The future T-931 compatible UOW must call it on its actual
ReadCommitted transaction before every factory/callback; this task does not edit
or weaken the original legacy constructor. Startup success is not cached authority.

Checks require exact current/session runtime identity, private database/migration
owner, original two-column ledger shape and complete single clean head rowset;
owner mechanics marker/default; exact baseline template/shared/base hashes and
provenance references/request; complete ordered receipts, manifest/SQL hashes,
predecessors and feature identities; and the complete feature-marker set.
Immutable historical installing-profile hashes need not equal a later release
profile. Their nonzero digests, unique nonzero installation requests, finite
completion time and valid provenance remain required. History guards must be
present/enabled with the expected type and owner-local non-definer functions.
RLS is unsupported on required objects so it cannot hide rows from complete
metadata comparisons. Catalog/permission/query/cancellation failures fail closed.

Typed grants are both required and maximum permission sets: exact table SELECT,
INSERT, UPDATE, DELETE or exact column SELECT/INSERT/UPDATE, with no implied CRUD
default. Core mechanics and metadata grants remain fixed. Required objects must
exist as ordinary tables with the exact owner and required schema access. Check
rejects privileged/owner/system roles, every transitively reachable membership
including NOINHERIT, foreign owner database access, schema/database CREATE/TEMP,
PUBLIC/delegated grants, forbidden table and column writes, REFERENCES/TRIGGER/
TRUNCATE/MAINTAIN, function/sequence access, broader defaults and access to
undeclared objects or schemas. Feature schema contracts/tests retain ownership
of column types/constraints and business authorization; this is not a full dump
or malicious-administrator tamper-proof equivalence proof.

Supported-profile boundary: every declared feature marker currently requires a
nonempty, disjoint table-grant contract. Marker-only features and overlapping
table contracts (even across distinct marker identities) fail closed. Historical
marker completeness does not authorize implicit union or supersession of current
grants. Any future schema revising an existing feature table or needing marker-only
grants requires an explicit coordinator-approved refinement before assignment;
this task does not claim that every future owner schema fits this representation.
The first actual auth schema does not yet exist, so no production T-059
compatibility is claimed by the disjoint synthetic `[1,12,17]` fixture.

Supported shared profiles are exactly the original base alone, or additive
legacy revisions `[1,2]`, `[1,2,3]`, `[1,2,3,4]`, with exact reviewed filenames,
hashes, applicable owner/runtime/format marker values, named objects and grants.
Undeclared known later markers and accessible undeclared objects reject readiness.
No maximum-revision inference or marker-existence-only fallback is used.
Custody and any revision above 4 return `ErrUnsupported`; T-934 owns that separate
extension after T-928. The approved generation-label forward correction is not
implemented here. Readiness proves no source admission, receiver bootstrap,
sealing policy, business effects, channel fence, broker ACK or assembled service.

The outer release authority must supply reviewed complete profiles and accepted
baseline evidence. Shape checks and SQL hashes do not authenticate an attestation,
prove historical execution or stopped processes, or authorize production policy.
No real baseline, feature schema or release bundle is approved by these fixtures.

1. **Effective defaults:** readiness now evaluates PostgreSQL's built-in defaults
   when no global ACL row exists, the explicit global replacement when present,
   and additive per-schema ACLs. All six default-ACL families are checked:
   tables, sequences, functions, types, schemas and large objects. Sequence
   catalog code `S` is deliberately mapped to `acldefault` code `s`. Any

   a compatible installation must explicitly deny future PUBLIC function EXECUTE

   The fixture establishes those prerequisites; no immutable migration artifact
   or production store was changed. PostgreSQL
   documents these distinct [global/schema semantics](https://www.postgresql.org/docs/18/catalog-pg-default-acl.html)
   and [built-in ACL codes](https://www.postgresql.org/docs/18/functions-info.html#FUNCTIONS-ACLITEM-FN-TABLE).
2. **Unconditional guards:** required triggers must have no predicate, arguments,
   UPDATE-column filter, constraint/deferral/parent/transition-table metadata;
   their original event/granularity/function/owner identity still must match.
   Expected owner-local functions retain invoker execution and their exact
   `search_path=pg_catalog` setting, and the checked session must use origin
   replication mode. Every reachable runtime role is denied SET/ALTER SYSTEM
   privilege on `session_replication_role`, preventing a later trigger-mode
   bypass after successful readiness. Enabled origin/always guards are supported;
   replica-only or disabled guards fail. This checks [execution metadata](https://www.postgresql.org/docs/18/catalog-pg-trigger.html),
   without claiming arbitrary trusted-administrator function-body equivalence.
3. **Original manifest format:** raw JSON is checked before normal decoding can
   replace malformed Unicode or discard overwritten members. Reject invalid
   UTF-8, lone/reversed/unpaired escaped surrogates, and duplicate decoded keys
   at any nesting depth, including unknown or subsequently overwritten values.
   No Unicode normalization occurs. The declared outer and nested field names
   are exact, so `owner`/`Owner`, `Version`/`version` and escaped aliases cannot
   silently target one Go field. Existing canonical manifests and valid escaped
   spellings of their exact names/values remain accepted. Unknown fields,
   missing declared fields, trailing data, typed identity mismatch, historical
   SQL/manifest hashes and all unsafe-file checks remain fail-closed.
