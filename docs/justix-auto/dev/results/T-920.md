## Observed storage and API evidence

The approved messaging-delivery contract §6 requires an immutable approved
deployment membership version, complete inert projection/process claims even
when an executor is down, installed-versus-admitted startup checks, and fenced
atomic admission/bootstrap/backlog cutovers. Conflicting versions must not race
to select the child set. Old message enrollment sets remain immutable.

At the inspected base:

- `pkg/eventstore/migrations/000002_messaging_delivery.up.sql:56` defines local
  admissions with stream/consumer identity, contract ID/version/digest, schemas,
  authority/scope/purpose/bootstrap references, bounds, kind and generation.
  It has no deployment membership version, complete catalog digest, or complete
  membership transition/request receipt.
- The same migration stores `membership_version` only in `dispatch_messages`
  (line 161) and `dispatch_enrollments` (line 171). The initial enrollment check

  neither row. `messaging_cutovers` is the explicit legacy-to-custody migration
  record and cannot be repurposed as runtime membership storage.
- `000004_projection_checkpoint.up.sql:117` adds per-consumer bootstrap
  identity and an installation request; the checkpoint is per consumer/stream.
  Neither this row nor the revision-4 compatibility singleton supplies a
  complete owner membership version or catalog transition history.
- `pkg/projection/checkpoint.go` exposes `NewCheckpoints` and
  `InstallBootstrap`, bound to the actual caller transaction and
  `eventstore.PreparedFences`. Exact bootstrap request replay checks the
  bootstrap and contiguous checkpoint; it is not a complete membership receipt.
- `pkg/eventstore/receiver_fence.go` provides an exclusive catalog fence and
  receiver fences sealed to the actual ReadCommitted transaction. These
  serialize cooperating operations but retain no version after transaction end.
- T-746 is an approved registration contract, not an existing shared catalog
  implementation. Its inert claims include feature/consumer ownership,
  subscription identity, resolved exchange/queue, routing/schema sets, and
  exact bound-output matching. Local admission rows do not retain that full
  identity. Claim presence alone is explicitly not data admission.

## Concrete empty-stream counterexample

1. The authenticated source issues an approved new-empty proof for `h=0`.
   Profile V1 contains complete consumers A and B, with approved subscription
   contracts and explicit process catch-up authority where applicable.
2. A fenced transaction could insert their local admissions, bootstrap rows,
   snapshots where required, and checkpoints. There are no messages above h,
   so there are no dispatch messages or enrollment rows to carry V1.
3. After commit and restart, another profile V2 can present the same retained
   per-consumer admission fields but a different approved deployment version or
   full catalog/binding identity. The existing stored state cannot distinguish
   V1 from V2. Comparing only consumer names/contracts cannot implement the
   specified exact admitted-version readiness check.
4. Serializing both attempts with the catalog advisory fence does not repair
   this missing durable distinction. A commit whose response is lost likewise
   cannot be reconciled against an exact complete membership request/version
   receipt. A transition adding zero consumers and encountering no retained
   messages cannot use new enrollment rows as a surrogate receipt either.

This is a source/schema counterexample, not a reproduced PostgreSQL runtime
failure. No SQL session, migration or fixture was executed for this report.

Encoding new structured metadata inside `authority_ref`, `bootstrap_ref`,
`contract_id` or generation would invent an unapproved protocol. Creating a
synthetic business event, dispatch message, inbox receipt or checkpoint would
fabricate history. Choosing the newest observed message would not prove an
admitted version or contiguous source high-water. None was implemented.

## Required architecture handoff before implementation resumes

The handoff must explicitly assign storage and define how to persist and verify:

- Exact owner membership identity: approved immutable version, canonical complete
  inert claim identity/digest and its normalization/duplicate rules, including
  projection and process claims independent of executable availability. Define
  full versus per-stream identity and empty-set authority rather than infer it.
- An evidenced membership transition with stable request identity and an exact
  input digest, prior admitted identity/expected revision, resulting identity,
  complete affected stream set and source-issued bootstrap/cutover evidence.
  Specify an authoritative current-state read and retained transition history.
- Atomic activation under the existing catalog/receiver lock order: current
  authority revalidation, all required bootstraps/snapshots/admissions, finite
  authorized retained backlog coverage, appended enrollment sets and all jobs.
  Missing bytes or invalidated completeness must abort activation and require
  source recovery outside SQL locks. Process catch-up must remain explicitly
  authorized; a projection snapshot cannot authorize historical commands.
- Exact duplicate and unknown-commit reconciliation, including different
  payload under the same request, concurrent competing versions, first
  installation with no dispatch rows, and transitions adding zero consumers.
  Define stale-profile behavior without automatically retrying an ambiguous
  transition or deriving success from per-consumer bootstrap receipts alone.
- Removal/drain/hold transitions that preserve old obligations and consumer
  meaning, with exact disposition authority. Specify whether and how future
  membership changes interact with old profiles, closed ranges, holds and
  current admission without rewriting any existing frozen set.
- Forward-only compatibility, exact artifact/marker lineage and narrow runtime
  privileges. Preserve existing migration bytes, admissions, bootstrap requests,
  message/enrollment sets and jobs. Never infer missing historical membership
  from old rows; any retained-installation adoption requires an explicit rule.

These are requirements for a proposal, not a proposed schema approval or added
task ownership. The coordinator owns architecture assignment, dependency changes
and canonical task transitions.
