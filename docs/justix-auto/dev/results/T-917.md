## Schema handoff for T-918/T-920/T-922/T-923

All tables are private to the database owner under `eventstore`.

| Record | Adapter-facing shape |
|---|---|
| `messaging_mode` | Singleton `owner_service`, `runtime_role`, `mode` (`legacy` initially), `schema_version=2`. Runtime SELECT only. |
| `messaging_admissions` | `admission_id` UUID; namespace `source-recipient` or `local-consumer`; concrete `source_owner/aggregate_type/aggregate_id`; `subject` destination or consumer name; `action=admit/close/hold/resume`, `prior_admission_id`; `contract_id/version/digest`; `schema_allowlist` array of distinct, source-qualified versioned event-type strings; `authority_ref/scope_ref/purpose/bootstrap_ref`; `start_after/end_inclusive`; local `consumer_kind/generation`; immutable creation time. |
| `outbox_messages` | Event UUID PK; unique source/aggregate/integration sequence; original `envelope` bytea and checked SHA-256; immutable `recipients` array and `plan_authority_ref`; creation time. |
| `outbox_deliveries` | PK `(event_id,destination)`; immutable parent/admission, exchange and route; mutable attempts, next attempt, lease owner/until, sent time and hold reference. |
| `dispatch_messages` | Event UUID PK and unique source stream sequence; bytes/hash, source-target route, initial `membership_version`, receiver `admission_ref/bootstrap_ref`, `initial_enrollment_id`. |
| `dispatch_enrollments` | PK `(event_id,enrollment_id)`; immutable membership version, cutover reference and exact `consumers` array. Initial enrollment is a deferred composite FK from its message; later consumers use additional enrollments. |
| `dispatch_jobs` | PK `(consumer_name,event_id)`; composite enrollment FK; immutable admission UUID, consumer kind/generation; scheduling, hold/quarantine refs, nullable completion and own composite inbox reference. |

Normal recipient array entries are exactly
`{"destination":"retail","admission_id":"<uuid>"}`. Migration-held entries
instead use `legacy_event_id`, referencing preserved migration evidence, and
cannot have an admission ID. Both arrays retain duplicate entries so deferred
checks reject duplicate destinations rather than silently coalescing them.
Consumer array entries are exactly
`{"consumer_name":"<stable name>","admission_id":"<uuid>"}`.
Child checks compare the entire sorted arrays, including immutable references;
missing, extra, duplicate or unaccounted children fail the transaction.
An explicit empty plan still needs a nonempty authority reference; SQL syntax
does not authorize that empty set.

Admission references transitively freeze contract and scope evidence. Basic
namespace, source/subject, admitted interval, schema allowlist, consumer kind and
generation checks run in SQL. Effective admission ranges, overlaps, closures,
hold/resume authority, snapshots and zero-checkpoint proof remain the typed
T-918/T-920 adapter's responsibility under the same sorted T-009 stream fences.
The schema does not establish business data permission by accepting a string
reference. No actual admissions or production defaults are installed.

Completed jobs must reference their own inbox `(consumer_name,event_id)` and
the inbox hash must match custody bytes. Completion cannot be cleared or changed.
Held/quarantined jobs cannot newly complete. The SQL FK/trigger cannot prove
that an effect and checkpoint occurred: T-922/T-923 must compose inbox, effect,
checkpoint and completion inside one lease-fenced transaction, including existing
legacy inbox recovery. It is insufficient to expose the scheduling UPDATE as a
freely callable completion API.

Custody-mode inbox INSERT requires the transaction adapter to execute
`SET LOCAL justix.messaging_mode='custody'`. Legacy mode needs no setting.
This is an explicit compatibility fence, not a credential or authorization claim.
New message/work INSERT and UPDATE require custody mode; old outbox writers and
relay UPDATE fail after cutover. Broker ACKs on already-existing legacy inbox
duplicates cannot be prevented by a SQL INSERT trigger: old consumers must be
stopped, their channels closed, and compatible compositions checked before
activation. T-922 and owner composition remain prerequisites.

## Explicit migration and retained legacy obligations

Installation creates the new schema in **legacy mode** and copies nothing.
The separately invoked, SECURITY INVOKER migration-owner function is:

```text
activate_messaging_custody(
  cutover uuid, new_schema_hash bytea, old_schema_hash bytea, backup text,
  stopped_runtimes text, broker_and_checkpoints text, compatibility text)
```

The caller must supply reviewed evidence references for a recoverable backup,
schema hashes, stopped old runtimes/AMQP channels and remaining confirm ambiguity,
inbox/checkpoint/backlog state, and schema/ACL/catalog/bootstrap compatibility.
SQL validates required reference presence and digest lengths; it cannot verify
that an external backup exists or a RabbitMQ channel is closed.

Migration authority stages one `messaging_legacy_authorizations` record per
legacy event: observed destination, immutable authority reference, and either a
validated source admission UUID or an explicit historical-authority-unavailable
hold reference. Stage reviewed authorization records and invoke cutover in one
transaction so invalid proposed evidence rolls back. Committed evidence is
immutable; correcting it is an explicit forward migration decision, never a
silent UPDATE in this script.

Cutover takes exclusive locks on legacy outbox/inbox and the mode fence, rejects
unknown or unreviewed routes, then preserves row counts and `to_jsonb` snapshots
of every original outbox row in owner-local `messaging_cutovers` and
`messaging_legacy_evidence`. No private bytes are exported to logs. Each original
row becomes one immutable parent and its exact observed destination child.
Bytes, hashes, IDs, sequence, creation time, prior attempts/next attempt and that
child's prior sent status are retained. Old leases remain in immutable evidence;
new active lease columns are reset. An unconfirmed child is retryable only with
an admitted route; absent historical authority retains a hold that scheduling
UPDATE cannot clear or fake as sent. No additional recipients are inferred.

Legacy rows and inbox entries remain in place. Cutover revokes table **and
column** outbox write grants, then audits every SET ROLE reachable identity for
remaining write access. New immutable records grant runtime SELECT/INSERT only;
migration control/evidence is SELECT only. Work UPDATE columns are enumerated.
Installation audits elevated/NOINHERIT membership, schema CREATE, broad and
column grants, default grants and cutover EXECUTE permission. Runtime receives
no DELETE, TRUNCATE, DDL, content UPDATE or activation capability. Reverse mode
transitions are rejected. No destructive down migration is supplied.
