## Implemented contract

`NewQuarantine` requires the exact integrated revision-5 compatibility marker,
the installed owner/current narrow runtime and an injected `EvidenceSecurity`
port. `Capture` clones arbitrary bytes, computes their exact SHA-256 and length,
and invokes sealing before SQL. There is no default sealer, plaintext fallback,
raw-body column or error-string persistence. The adapter accepts only safe reason
codes and typed trusted context. It commits one immutable evidence row and root
hold action under stable evidence/request advisory serialization. An exact
request replay reads the retained receipt; changed bytes, context, identity,
policy/key/format or hold evidence conflict.

`CaptureAndAcknowledge` exists only for intake/direct-handler deliveries. Its
single-delivery ACK callback runs after a known commit or exact committed receipt.
Seal, validation, SQL, rollback and unknown-commit errors never call ACK. An ACK
failure returns the committed receipt with `ErrQuarantineAcknowledgment`, so
redelivery can reconcile rather than discard evidence.

Custody-handler capture takes the owner receiver fence plus declared generation/
guard fences before the exact job row. A new unfinished capture requires the
matching live lease, verifies the retained dispatch message through the migration
guard and atomically installs only `quarantine:<evidence UUID>`. It does not write
inbox/completion/checkpoint fields. A completed race is recorded with the actual
completed observation and cannot reopen the job. Exact retained request recovery
does not falsely require that the old lease still be live.

`Redriver.Request` calls the injected current-authority port before appending a
request to the exact current audit tip. Request/result chains serialize per
evidence; changed replay and forks conflict. `Execute` reauthorizes before
restoring, verifies restored length and SHA-256, then hands copied bytes to an
injected ordinary intake/inbox/job adapter. Accepted results cite a typed durable
receipt which the revision-5 SQL trigger checks independently. Crash after the
ordinary effect but before result journaling re-enters ordinary dedup; an already
committed result is returned without invoking the path again. Denial, restore
failure and ordinary failure retain safe result evidence without fabricated
success.

Custody release verifies restored original bytes, reacquires the receiver and
declared fences, locks the exact incomplete job and atomically appends `released`
while clearing only its matching quarantine reference. It preserves independent
`hold_ref`, does not complete the job and leaves later execution to T-923.

## Fix cycle 1 — bind tickets before restore/effect

Independent QA reviewed exact original commit
`b71337b3419f27e0d6f52891a0ba7c7c31a7553b` and returned BOUNCE for one P2.
A legitimate ticket created by Redriver A could be passed to Redriver B. B read
its own same-UUID evidence and invoked `OrdinaryRedrive.Apply` before the later
result insert noticed that B lacked A's request action. Two isolated databases
with colliding UUID/context and different protected bytes reproduced an external
callback before the conflict. The original QA report and overlay remain
unchanged as evidence.

`RedriveTicket` is now sealed to the exact creating `Redriver` composition.
Before `Execute` or `ReleaseCustody` can restore protected bytes, invoke current
authorization, run an ordinary callback, or change a job reference, the receiving
adapter requires that identity and performs a transactionally consistent local
proof of:

- the exact immutable evidence snapshot retained in the ticket, including the
  original digest/length and protected ciphertext/reference identity; and
- the exact local `redrive-request` action, request identity, prior action,
  actor/authority/scope/purpose/repair/manifest and intended path/consumer.

Foreign-store, foreign-composition, missing-request and changed-snapshot tickets
therefore fail with `ErrRedriveConflict` at the pre-effect boundary. A process
restart can recover by replaying the exact durable `Request` through the newly
constructed redriver and receiving a newly bound ticket; it cannot reuse stale
in-memory authority. The same check applies to custody release.

The owned regression creates two isolated owner-local PostgreSQL stores with the
same canonical evidence/request IDs and different protected bytes. A ticket from
A passed to B leaves the ordinary callback count at zero. The custody case also
passes a ticket to another redriver composition over the same DB and proves the
job reference is untouched. The prior crash test now injects a panic immediately
after the ordinary inbox commit, then reuses the same redriver/ticket/result IDs;
retry reaches inbox dedup and one accepted result without weakening store binding.
