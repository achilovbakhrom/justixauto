## Findings

### P1 — runtime parameter privilege bypasses trigger and FK protection

The runtime capability audit in
`pkg/eventstore/migrations/000006_projection_generation.up.sql:55` and `:399`
checks role attributes, memberships, object grants and defaults, but never
checks effective SET permission on `session_replication_role`.

On a disposable PostgreSQL 180006 database with every real prior migration,
the independent probe grants only this extra capability as the fixture admin:

```sql
GRANT SET ON PARAMETER session_replication_role TO <runtime>;
```

`has_parameter_privilege(...,'SET')` returns true. The complete unmodified
000006 migration nevertheless commits. The ordinary runtime then commits:

```sql
BEGIN;
SET LOCAL session_replication_role=replica;
INSERT INTO eventstore.projection_heads
  (projection_name,epoch,active_generation_id)
VALUES (<fresh projection>,77,<fresh absent generation UUID>);
COMMIT;
```

A fresh runtime read returns the epoch-77 head and the nonexistent generation
UUID. There is no generation row, switch evidence, initial epoch-one state or
matching foreign key. This is a demonstrated runtime bypass, not hypothetical
trusted-owner DDL tampering. The probe revokes its explicit parameter grant
afterward and the owned fixture is removed. The installer must fail closed for
effective direct, PUBLIC and SET ROLE-reachable trigger-bypass privileges;
ordinary safe installations must still pass. Do not rewrite prior SQL artifacts
or silently revoke deployment privileges inside this forward script.

### P2 — deferred checks can be flushed before final pointer state

The `DEFERRABLE INITIALLY DEFERRED` receipt trigger at SQL `:338–359` is treated
as an unavoidable transaction-final check. An ordinary runtime may execute
`SET CONSTRAINTS ALL IMMEDIATE` and then `SET CONSTRAINTS ALL DEFERRED`.
No extra grants or altered trigger definitions are needed.

The probe starts with an active generation at epoch 2 and, in one transaction,
inserts matching hold evidence and updates the head to epoch 3, flushes the
constraint, restores deferred mode, then inserts another matching hold and
updates the head to epoch 4. COMMIT succeeds with both receipts retained. The
first receipt no longer matches the final head. The same two steps without the
flush are rejected by the committed author test, so the claimed one-pointer-
change-per-projection-per-transaction boundary is not enforced consistently.

A second independent case inserts an inactive-generation hold, flushes its
check while the head is inactive, restores deferred mode, appends build and
validation evidence, then activates that generation in the same transaction.
COMMIT succeeds without a head hold. This evades the same final-state rule that
the trigger normally applies to an inactive hold becoming active by commit.
These are two reproductions of one timing flaw, not two unrelated findings.

Preserve the approved evidence/CAS protocol under caller-controlled constraint
timing, including rollback/savepoint paths. Do not claim these triggers run only
at commit or silently broaden the supported pointer protocol. A fix needs new
exact-commit tests retaining these counterexamples.

### P2 — required checkpoint column UPDATE privileges are not audited

The required-grant checks at SQL `:382–398` cover schema USAGE and table
SELECT/INSERT. The named column list at `:422–434` is only a maximum grant
allowlist; it does not require the permitted checkpoint updates.

The probe executes, as the isolated migration owner:

```sql
REVOKE UPDATE(position) ON eventstore.consumer_checkpoints FROM <runtime>;
```

The effective `has_column_privilege(...,'position','UPDATE')` is false, but the
complete 000006 installation commits with its compatibility marker. The runtime
cannot perform the required contiguous checkpoint advance. This violates the
task's fail-closed required-grant prerequisite. Verify applicable required named
mutable columns as well as forbidden grants, preserving the distinction between
legacy and custody privileges. Do not repair prior ACLs automatically.
