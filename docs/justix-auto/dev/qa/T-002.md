## Required corrections

1. **P1 — specify the restricted recovery proof handoff.** The proposal's password
   reset row (line 22) requires TOTP or a recovery code, but the approved HTTP
   contract has only `{token,newPassword,confirmation}` at
   `/session/recovery/complete` (http-domain.md:67). The existing MFA verify route
   accepts a login challenge and returns a session; it does not establish a
   recovery-purpose proof or accept a recovery-code variant. A caller who forgot
   their password cannot obtain the ordinary password-authenticated challenge.
   Add a proposed contract delta or an explicit compatible restricted-challenge
   sequence: exact proof input, browser/challenge/user/purpose/security-version
   binding, allowed next action, and atomic consumption with credential change
   and session revocation. Cover concurrent completion, failed validation before
   consumption, stale security version and a lost completion response without
   putting authentication responses in generic command receipts. Also state
   whether a recovery code can authorize MFA re-enrollment after factor loss or
   only password reset; the current text promises a restricted flow without
   defining its authority. Keep all proposed deltas unapproved until promoted by
   the coordinator after the relevant acceptance.

2. **P2 — define delivery retry storage and the token handoff.** Lines 22/25
   combine digest-only reset-token storage with internally retryable delivery.
   After a process crash, a digest cannot reproduce the token for a retry. State
   whether a bounded, encrypted identity-private delivery record is proposed, or
   whether retry issues a replacement token with explicit invalidation semantics.
   Specify lost delivery acknowledgements, duplicate emails and expiration so a
   retry cannot silently create multiple independent reset authorities. Line 30
   also prohibits tokens in URLs: explicitly select a manual copy/paste code
   handoff or another compatible transport; do not leave the implementation to
   invent a token-bearing link. Generic events/outbox payloads, logs and receipts
   must remain secret-free. Production mail configuration can stay deferred.

3. **P2 — make invitation eligibility reviewable.** Line 24 requires a verified
   matching identity, consistent with `/invitations/accept`, but neither the
   proposal nor the baseline supplies initial email verification/credential setup
   for the pending user created by `/admin/users`. State that this proposal only
   admits already credentialed, previously verified identities, with pending-user
   activation separately gated, or propose the exact bounded activation and
   independent email-proof sequence. In either case, preserve token binding to
   invitation/company/email, revocation/expiry checks and atomic one-use membership
   creation. This does not call for public registration or account linking.

One wording correction should accompany those changes: TOTP line 19 says
"plaintext only during enrollment". Ordinary local TOTP verification also needs
the secret transiently in protected process memory. Distinguish enrollment-only
disclosure to the browser from server-side decryption for verification; retain
encryption at rest and no logging. This is not a request to disclose secrets.
