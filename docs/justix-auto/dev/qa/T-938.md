## Finding: Unicode map traversal changes semantic outcome across Go/TS

**P2, reproducible.** `tools/generate-contracts.mjs:511` emits TypeScript default
`Object.keys(value).sort()`, which orders UTF-16 code units. The generated Go
walker calls `contractAuthKeys` (`:769–771`), whose `sort.Strings` at `:810` orders
UTF-8 bytes. Ordinary valid keys U+E000 and U+10000 consequently reverse order.

The independent fixture uses the existing emitted Envelope map of named Leaf
values and adds:

```json
{"\uE000":"bmp","\uD800\uDC00":"supplementary"}
```

The same pure Leaf rule returns `mismatch` for `bmp`, `fatal:policy` for
`supplementary`, and `valid` otherwise. Actual emitted strict TypeScript and Go
race-tested code disagree:

| Probe | Go | TypeScript |
| --- | --- | --- |
| All hooks valid: Leaf values | ordinary, bmp, supplementary | ordinary, supplementary, bmp |
| Above rejection rule: first failing value | bmp | supplementary |
| Full validation outcome | mismatch | fatal:policy |

Both runtimes reject this example; this is not a demonstrated acceptance bypass.
It violates the task's semantic parity and deterministic per-occurrence behavior:
ordinary mismatch versus fatal policy can drive different caller handling. The
existing 33-row parity corpus checks hook names, and its map values use ASCII
keys, so it does not expose this difference.

Use one explicit cross-language Unicode ordering for auth object/map traversal,
and preserve this failing case as an emitted-runtime regression comparing hook
values and outcomes. Preserve the legacy generator bytes and all inert barriers.
No implementation fix was attempted by QA.

Reproduction: [independent_test.go](T-938/independent_test.go) overlaid onto the
