## Finding P2 — failed Docker start reply leaves the owned fixture running

`pkg/eventstore/quarantine_migration_test.go:50–53` runs Docker before registering
cleanup. If Docker allocates/starts the container but the CLI returns an error,
`t.Fatalf` exits without registering any cleanup. This also bypasses the later
mount validation and absence verification.

The [independent failure probe](T-927/fixture_failure_probe_test.go) wraps only
the child test's Docker call. It executes the real pinned, UUID-named tmpfs
fixture creation, captures the actual returned ID and original `--name`, then
returns synthetic exit 42 to model a lost successful-start reply. The child
failed as expected, but independent inspection found its container still
running. This is an observed failure path, not an assumed Docker outcome.

Evidence: [complete failed attempt](T-927/fixture-failure-attempt1.log).
The leaked test container was
`4f8aa829bf4ed6698ad0f8cbbd78272d1e915333bf27618c423ac18acd57b0e8`, name
`justixauto-t927-dc8f78aa-71eb-43b2-91f7-41edebbb8b44`.
QA's parent cleanup was registered before the child ran. It validated the exact
captured ID, UUID name, pinned image and absence of volume mounts, removed only
that object, and verified its absence. No fixture from this probe remains.

Required bounded correction: establish failure-safe cleanup before attempting
creation, validate the exact owned identity and mounts, and verify cleanup even
when creation/start returns an error after allocation. Do not use an arbitrary
ID parsed from error text or remove an existing unrelated object. Add a retained
failed-start/lost-reply regression and rerun exact-commit QA. No SQL change is
requested by this finding.
