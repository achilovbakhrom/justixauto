## Findings

1. **P1 — AppendAttempt accepts a different retained consumer identity.**
   `pkg/projection/checkpoint.go:517` selects the gap by K, then line 526 checks
   only checkpoint/bootstrap UUID equality. It never calls `bootstrap(ctx)` to
   compare the adapter's kind, generation, contract ID/version/digest with the
   retained bootstrap. Under the same local owner, consumer and source stream,
   five independent live cases changed exactly one of those fields. `FindGap`
   correctly returned `ErrReconciliationHold` for each changed identity, but
   `AppendAttempt` returned nil and committed a `held` successor in every case.
   Thus a stale or miswired consumer contract can change another incarnation's
   recovery chain and prevent its requested tip from being fetched. SQL's K/FK
   checks and the mandatory current-authority callback do not establish this
   missing mechanical identity comparison. The callback used here explicitly
   grants synthetic authority; the expected rejection is the shared adapter's
   independent retained-identity check, as in its other methods.

   Reproducer: `T-014/independent_test.go`, five
   `TestIndependentT014/changed-identity-*` cases; evidence
   `T-014/independent-output.txt`. Each reports `error=<nil>` and
   `persisted_attempts=1`. Revalidate the retained bootstrap and contiguous
   checkpoint identity in the append path before a new attempt or replay can
   succeed; preserve exact-replay semantics. Add regression coverage for all
   five identity fields and verify unchanged-identity replay still succeeds.

2. **P2 — disposable fixture leaves PostgreSQL anonymous storage behind.**
   `pkg/projection/sequence_test.go:1258` removes its container with `docker rm
   -f`, omitting volume cleanup. Live inspection of this exact fixture confirms
   the pinned image creates an anonymous volume. The result's statement that it
   touches no persistent volume is therefore inaccurate. Use cleanup restricted
   to this fixture's attached anonymous volumes (for example `docker rm -fv`)
   and verify removal. The independent QA wrapper inspected and removed only its
   exact volume `9d8e3ed6377366ca6076981dfddafd75df7142bd1168de0a191ddd072d5f95da`
   after fixture teardown; a subsequent inspect returned `no such volume`.
   The earlier baseline run did not retain its volume identity, so QA did not
   guess ownership or prune unknown Docker volumes. No T-014 container remains.
