## P2: custody mode can pass the legacy readiness check

`services/retail/adapter/postgres/unit_of_work.go:68` validates the old required
outbox permissions but never explicitly rejects an installed custody mode.
The normal activation revokes those permissions, so the committed test passes.
If the migration owner accidentally restores only the old narrow grants,
the unsupported installation becomes ready and reaches feature construction
and execution. This is a configuration-drift probe, not a claim that the
runtime can grant itself privileges or bypass the database's custody triggers.

Reproduction uses the actual unchanged shared schema, Retail migration and
`000002_messaging_delivery.up.sql` in an isolated PostgreSQL 18.6 fixture:

1. Install clean Retail v1 and the additive migration; legacy readiness passes.
2. Activate custody with the actual owner function; normal readiness rejects.
3. As the migration owner, restore only these previously supported grants:

```sql
GRANT INSERT ON eventstore.outbox TO justix_retail_runtime;
GRANT UPDATE(attempts,next_attempt_at,lease_owner,lease_until,sent_at)
  ON eventstore.outbox TO justix_retail_runtime;
```

4. Verify `eventstore.messaging_mode.mode = 'custody'` remains unchanged.
5. Call the same runner's Check and Run.

Both independent executions observed:

```text
incompatible installation reached feature: Check=<nil> Run=<nil> binds=1 calls=1
```

Expected: `ErrIncompatiblePersistence` before either the factory or callback.
The explicit legacy-only contract should gate any present messaging mode,
while preserving supported installations that predate the additive table.
This requires a bounded Retail fix and regression, not silent T-930 profile
integration, migration changes or repairs to other owner scaffolds.
