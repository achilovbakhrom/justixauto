## Blocking finding: explicit null declarations bypass closed auth validation

`tools/generate-contracts.mjs:235` calls
`security(op.security ?? document.security ?? [], internal)`. A marked auth
operation containing **`security: null`** is therefore accepted as if the field
were omitted. Without document security the trusted model contains `[]`; with
document cookie security it silently inherits that requirement instead. The
security validator never sees the supplied invalid non-array declaration.

The same normalization occurs at line 237 for `op.parameters ?? []`. A marked
GET `/api/v1/identity/session` containing **`parameters: null`** is accepted with
an empty parameter list, bypassing the explicit array check at line 240.

All three observations are reproduced from the actual private compiler in
[probe-output.json](T-937/probe-output.json), under `findings`. This violates the
task's closed header/security/semantics model requirement: omitted optional
fields may receive defaults; explicitly malformed values must reject. No output
activation leak was found—the public CLI and both renderers still reject auth.
The risk is admitting malformed declarations into the trusted model that later
serial tasks will consume.

Apply bounded presence/type checks to marked auth operations before fallback.
Preserve legitimate omission/inheritance, explicit valid empty security arrays,
ordinary class-free JSON declarations and legacy non-auth behavior/output.
Add negatives for null operation security with and without document requirements
and null GET parameters; retain the approved anonymous alternatives and unsafe
injected-CSRF cases. No unrelated generator refactor or runtime activation is
required. A new exact-commit review is needed after correction.
