## Blocking finding

The missing-credential guard does not fail PostgreSQL 18 initialization.
`infra/local/postgres/init-owners.sql:27` uses `\\quit 3`, but PostgreSQL
18.6 `psql` does not accept an exit-status argument. It warns that the extra
argument is ignored and exits with status 0.

Direct reproduction against the exact pinned image:

```text
$ docker exec -e JUSTIXAUTO_DOCUMENTS_DB_PASSWORD= ... \
    psql -v ON_ERROR_STOP=1 -U postgres -d postgres \
    -f /docker-entrypoint-initdb.d/10-justix-owners.sql
All seven JUSTIXAUTO_*_DB_PASSWORD variables are required.
psql:/docker-entrypoint-initdb.d/10-justix-owners.sql:27:
warning: \\quit: extra argument "3" ignored
exit 0
```

An independent fresh container, `justixauto-t005-qa-missing-f80d8f2`, was
started from the exact approved digest with the documents password empty and the
other six synthetic passwords present. The official entrypoint logged both the
warning above and:

```text
PostgreSQL init process complete; ready for start up.
database system is ready to accept connections
```

`pg_isready` passed, while this catalog probe returned zero:

```sql
SELECT count(*) FROM pg_database WHERE datname LIKE 'justix_%';
-- 0
```

Therefore a configuration error can produce a healthy-looking local PostgreSQL
container with none of the seven required stores. This contradicts the README
and result claim that all seven injected credentials are required, and it breaks
the failure-recovery part of B-01.AC1. Replace the guard with a construct that
causes a nonzero `psql`/entrypoint exit on PostgreSQL 18, add a regression that
starts from an empty data directory with one missing value, then submit a new
commit for exact-SHA QA.
