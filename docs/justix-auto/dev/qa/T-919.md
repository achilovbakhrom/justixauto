## Source review and limits

NewMessage uses a typed schema and one serialization/hash. InsertMessages takes
sealed messages without a recipient-list or cached-plan argument, calls fresh
Resolve plus ValidatePlan in the same bound SQL transaction, and persists each
root admission ID with the sorted complete recipient set. SQL INSERT SELECT
matches the local event's owner, stream/revisions, type/version, company,
timestamp, actor and correlation/causation/operation metadata, with current-tx
xmin. Changed metadata, missing rows and child failures propagate to outer Run.
Explicit empty authority is stored when no recipient is admitted.

Both legacy/custody APIs check actual read-committed mode on empty input; custody
requires the exact owner/runtime and revision-3/format-1 marker hashes. Legacy
single-target compatibility is retained only for original or additive legacy
mode. The transaction marker is compatibility evidence, not authorization.
Constructor binding is inert and compares the actual transaction connection;
no nested commit, retry, publish or ACK is introduced.

This is an adapter-level GREEN, not owner runtime or end-to-end delivery
acceptance. The caller must Fence all streams before append/other stream locks,
submit every integration message, propagate errors and commit command receipts
and guards in the same outer transaction. The adapter cannot authorize business
data from fixture references or prove correct caller composition. Receipt lookup
and replay policy remain owner responsibilities after unknown commits. Complete
startup ACL checks, broker delivery, intake, logical effects/checkpoints and
operational readiness remain their assigned tasks. No RabbitMQ claim is made.
Historical T-918 short-route fixtures remain scoped to unmodified 000002; the
actual production route is tested separately against 000003.
